# 竞品调研与我们的差异（2026-11-10）

## 一、GitHub 上同类的现成项目（按环节分类）

| 环节 | 代表项目 | 做到什么程度 |
|---|---|---|
| 直播录制 / 弹幕 / 切片 | [biliLive-tools](https://github.com/renmu123/biliLive-tools) | 录制、弹幕、**手动**切片；自动切片主要依据弹幕/SC 关键事件，不是"找出歌" |
| 录播人工工作流 | [A-SOUL 录播打轴压制方法](https://github.com/djj45/asoul) | 图文教程，把"打轴/压制/投稿"串成人工流程 |
| 歌词对齐（音频→LRC） | [syncalong](https://github.com/wickeddoc/syncalong)、[LRCGen](https://github.com/final-wav/LRCGen)、[lyrics-sync](https://github.com/jossieb/lyrics-sync)、[python-lyrics-transcriber](https://github.com/nomadkaraoke/python-lyrics-transcriber) | 给**一首已知歌曲**的音频 + 纯文本歌词，输出带时间轴的 LRC/卡拉OK 字幕；多数依赖人声分离（Demucs）提升精度 |
| 卡拉OK字幕生成 | [py-roller](https://pypi.org/project/py-roller/) | 已有对齐结果 → 逐字卡拉OK字幕（含 ASS） |

**结论**：单点工具齐全，但没有一个现成项目完整覆盖"整场直播录播 → 自动找出哪些段落是歌 → 逐首切出来 → 配歌词排轴 → 质检 → 上站点播放"这条链路。

## 二、我们的差异（不是单点创新，而是链路与判据）

1. **面向"歌回"长录播的整场流水线**
   输入是一个 B 站录播 BV 号（含 P1/P2 分P），输出是每首歌的三件套（音频/LRC/逐字 ASS）+ 网站。
   现有工具要么只管录制切片（人来找歌），要么只管单曲对齐（歌已知、音频已切好）。

2. **切点与歌词彻底解耦（两套独立标准）**
   - 切点只用**音频静音 + "演唱"标签**决定（90–600s、5s 内无静音不许切、帧对齐）
   - 歌词只用于切完之后的独立验证，**不回改切点**
   - 避免"歌词认错 → 切点跟着错 → 质检又用同一份歌词自证"的循环依赖；这是我们在实战中踩出来的教训

3. **三重认歌核验（宁缺勿错）**
   多段纯中文片段检索网易云 → 候选歌词文字召回 ≥40% → 拼音 DTW 对齐率 ≥60% → 综合评分择优；
   另有**音频模型（MiMo）独立旁证**：抽首/中/尾三段确认"是否在唱这些词、有无杂谈、是否拼接"。

4. **可量化、可追溯的发布门槛**
   锚定率 ≥85%、歌词覆盖 ≥80%、文字召回 ≥66%、行同步率 ≥80%（±2s）、中位误差 ≤0.3s、
   单调递增、说话占比 ≤8%、编码/采样率/声道与源一致、时长偏差 ≤0.15s、EBU R128 只测不改。
   每首指标写入 `queue/qc_metrics.jsonl`，拦截原因写入 `queue/qc_rejects.json`。

5. **零重编码交付**
   切歌全程 `-c copy` 流复制，不重编码、不滤波、不做人声分离（用户明确要求"最真实的声音"）。
   多数卡拉OK项目会做人声分离再对齐——精度更高，但违背"原声"要求。

6. **歌回的工程细节**
   - 同一首歌在不同场次重复演唱 → 全部保留并标注场次日期与流内时间
   - 分P 逐P 处理、互不覆盖
   - 仅跳过舰长回/合唱回/连麦/毕业/生日会/游戏回

7. **无人值守**
   串行队列（systemd 独立服务）、内存闸门（重活互斥）、API 限流退避与自动恢复、
   断点续跑（转写/识别缓存、按成品路径去重）、每日自动报告。

## 三、独特性一句话

> 不是"发明了更好的对齐算法"，而是**把一条面向中文 VTuber 歌回的长录播生产链路做成可量化、可追溯、可无人值守的流水线**，
> 并且把"什么算合格"写成硬门槛——不达标宁可不发布。

## 四、我们明确的短板（诚实记录）

1. **排轴精度受限于本地 ASR**：MiMo 音频模型虽快（14× 实时）且文本更准，但输出粒度是 10–20 秒一句，无法替代 whisper 的 3–6 秒句级时间戳
2. **同步率指标是自洽的**：用同一份 whisper 时间戳做参照，不是独立真值；业界先进做法（WhisperX 音素级强制对齐，词级中位误差约 21ms）我们没上
3. **不做人声分离**：对齐精度上限低于分离方案（这是我们主动的选择）
4. **无 GPU**：2 vCPU 上 whisper small int8 是速度瓶颈（约 2~4× 实时）
5. **音乐结构分析缺失**：连唱串烧（两首之间无静音）可能切不开

## 五、可借鉴的改进方向

- 引入 wav2vec2/MMS 音素级强制对齐做**抽样真值评估**（不必全量），量化真实误差
- 用 beat/tempo 检测辅助"无静音边界"的串烧拆分
- 把"每首歌多次演唱"做成网站上的版本选择（已有批次标注基础）

## 六、MiMo 能否接手整场转写（2026-11-10 复测结论）

**能出细粒度句子，但时间戳不可信。**

| 实验 | 结果 |
|---|---|
| 120 秒块 + "逐句" | 11~13 句/2分钟（whisper 23~28 句）→ 太稀 |
| 60 秒块 + "按换气切分、每句≤8字" | 18~19 句/2分钟 → 粒度可比 whisper |
| 句级时间与 whisper 对比 | 中位差 **3~5 秒**，差 ≤0.5s 的只占 0~9% |
| 文本准确度 | 明显优于 whisper（简体、少错字） |

结论：**MiMo 适合"文本 + 粗判别 + 独立验收"，不适合作为时间轴来源**；
时间戳仍用本地 whisper（图内部自洽），MiMo 只做交叉验证与音频侧门禁。

另：早期"MiMo 输出太稀"的结论里有一半是解析 bug（它输出 `m:ss` 区间格式，
正文在下一行），解析器已修（支持 `12.3|歌词`、`0:02.6-0:11.0`+换行、`31.4-33.0 | SPEAKER_00: 歌词` 三种）。
